Architecture Style:     Layered/REST API with Controller-Service-Model separation
Core Purpose:          Two-sided marketplace connecting service seekers with 
                       service providers, featuring booking workflows, real-time 
                       notifications, and location-based service discovery

  * lastLogin (Date)
  * createdAt, updatedAt

- Purpose: Customer profile
- Key Fields:
  * user (ref: User, unique)
  * name (required)
  * gender (enum: male/female/other)
  * address:
    - street, city, state, pinCode
    - coordinates (GeoJSON Point, nullable)
  * profileImage
  * preferences (notifications, emailUpdates)
  * createdAt, updatedAt
- Indexes: address.city, address.state

SERVICE PROVIDER MODEL (ServiceProvider.js)
- Purpose: Service provider business profile
- Key Fields:
  * userId (ref: User, unique)
  * name, businessName
  * description (max 1000 chars)
  * experienceYears
  * businessAddress:
    - street, city, state, pinCode (all required)
    - coordinates: GeoJSON Point [longitude, latitude]
  * languages []
  * rating:
    - average (0-5)
    - count
    - breakdown {1-5}
  * startingPrice, emergencyCharge, extraChargeNote
  * isVerified (boolean)
  * verificationStatus (enum: pending/approved/rejected)
  * totalJobsCompleted, totalEarnings, platformEarnings
  * currentPlan (enum: Basic/Professional/Business/Enterprise/null)
  * planExpiresAt
  * businessImages [] (url, filename, originalName, uploadedAt)
- Indexes:
  * businessAddress.coordinates: '2dsphere' (geospatial queries)
  * isVerified, rating, businessName (text search)
  * city, state

BOOKING MODEL (Booking.js)
- Purpose: Core transaction between seeker and provider

  * seekerId (ref: ServiceSeeker, required)

### 3.5 AUTHENTICATION MECHANISM

JWT-Based Authentication Flow:
1. User submits credentials → POST /api/auth/login
2. Controller verifies password with bcrypt.compare()
3. JWT tokens generated via jwtUtils.generateTokens()
4. Token returned in response + stored in localStorage
5. Subsequent requests include: Authorization: Bearer <token>
6. Auth middleware validates JWT signature
7. User fetched and attached to req.user
8. Socket connections include JWT in handshake auth

Token Storage:
- Access token: localStorage ('accessToken', 'token')
- Also stored in cookies for redundancy

Password Security:
- bcryptjs with salt rounds (10)
- User schema has select: false for password field

### 3.6 ROLE-BASED ACCESS IMPLEMENTATION

Role Definition (User.js):
- enum: ['seeker', 'provider', 'admin']

Middleware Usage Examples:
- auth()                          → Any authenticated user
- auth(['provider'])              → Provider only
- auth(['seeker'])                → Seeker only  
- auth(['admin'])                 → Admin only
- auth(['provider', 'admin'])     → Multiple roles

Frontend Protection:
- ProtectedRoutes component checks:
  1. isAuthenticated
  2. user.role in allowedRoles
  3. profile?.isVerified for providers

### 3.7 DATABASE SCHEMA PATTERNS

Geospatial Queries:
- ServiceProvider: 2dsphere index on businessAddress.coordinates
- Booking: 2dsphere index on serviceAddress.coordinates

Compound Indexes:
- Booking: { seekerId: 1 }, { providerId: 1 }, { status: 1 }, { bookingDate: 1 }
- ServiceProvider: { isVerified: 1 }, { rating: -1 }, { city: 1 }, { state: 1 }

Referential Integrity:
- User → ServiceSeeker/ServiceProvider (one-to-one)
- ServiceSeeker → Booking (one-to-many)
- ServiceProvider → Booking (one-to-many)
- Booking → Notification (one-to-many)

Soft Delete:
- Status-based (no hard deletes)
- Booking status: pending → accepted → confirmed → in-progress → completed
- Or: rejected, cancelled, disputed

### 3.8 GEO-LOCATION IMPLEMENTATION

Geocoding Service (geocodingService.js):

Primary Provider: OpenStreetMap Nominatim API
- Free, no API key required
- Request: https://nominatim.openstreetmap.org/search
- Headers: User-Agent required
- Timeout: 5 seconds
- Retry: 2 attempts on timeout

Fallback Provider: Google Maps API
- Paid, requires GOOGLE_MAPS_API_KEY
- Request: https://maps.googleapis.com/maps/api/geocode/json

PIN Code Fallback:
- Lookup table for major Indian cities
- Ahmedabad: 382, 380 | Mumbai: 400 | Delhi: 110
- Bangalore: 560 | Hyderabad: 500 | Chennai: 600
- Kolkata: 700 | Pune: 411 | Surat: 395 | etc.

Default Coordinates:
- Ahmedabad: [72.5714, 23.0225] (when all geocoding fails)

Coordinate Format:
- GeoJSON Point: { type: 'Point', coordinates: [longitude, latitude] }

Distance Calculation:
- Haversine formula for km distance
- Method: calculateDistance(lat1, lon1, lat2, lon2)

Validation:
- Latitude: -90 to 90
- Longitude: -180 to 180
- Reject default India center [78.9629, 20.5937]

### 3.10 BOOKING WORKFLOW LOGIC

Phase 1: Creation (Seeker)
1. POST /api/bookings with providerId, serviceId, date, time, address
2. Validations:
   - Provider exists and isVerified
   - Provider service isAvailable
   - Booking date is in future
   - No duplicate booking (same provider, date, time)
   - Within provider's working hours (from ProviderSchedule)
3. Pricing calculation:
   - basePrice = providerService.minPrice || provider.startingPrice || 500
   - extraCharge = priority === 'urgent' ? basePrice * 0.5 : 0
   - platformFee = basePrice * 0.05
   - totalPrice = (basePrice + extraCharge + platformFee) * priorityMultiplier
4. Booking created with status: 'pending', paymentStatus: 'pending'
5. Notification created for provider
6. Socket event 'booking:new' emitted to provider

Phase 2: Provider Response
- Accept: PATCH /api/bookings/:id/accept
  * Status → 'accepted'
  * Notification + socket to seeker
- Reject: PATCH /api/bookings/:id/reject
  * Status → 'rejected'
  * cancellationReason stored
  * Notification + socket to seeker

Phase 3: Cancellation
- PATCH /api/bookings/:id/cancel
- Allowed statuses: pending, accepted, confirmed, in-progress
- Not allowed: cancelled, completed, rejected
- Either seeker or provider can cancel
- Notification + socket to other party

Status Flow:
pending → accepted → confirmed → in-progress → completed
    ↓         ↓
  rejected  cancelled

Pricing Breakdown:
- basePrice: Provider's minimum/service price
- extraCharge: 50% for urgent priority
- platformFee: 5% of base price
- priorityMultiplier: 1.5x for urgent

### 3.11 NOTIFICATION FLOW

Trigger Events:
- Booking created → provider notified
- Booking accepted → seeker notified
- Booking rejected → seeker notified
- Booking cancelled → both parties notified

Storage:
- MongoDB Notification collection
- Fields: userId, bookingId, title, message, category, type, isRead, actionUrl, metadata

Real-time Delivery:
1. Controller creates Notification document
2. socketManager.emitToUser(userId, event, data)
3. SocketContext receives event in frontend
4. Updates notifications array + increments unread count
5. UI re-renders with new notification badge

Read Status:
- GET /api/notifications → list with isRead
- GET /api/notifications/unread-count → count
- PATCH /api/notifications/:id/read → mark single
- PATCH /api/notifications/read-all → mark all
- DELETE /api/notifications/:id → remove

## 6. DATA FLOW EXPLANATION

### 6.1 AUTHENTICATION FLOW (End-to-End)

1. USER LOGIN:
   - User submits email/password to /api/auth/login
   - Controller finds user by email
   - bcrypt.compare(password, user.password)
   - If valid: generateTokens(user._id, user.role)
   - Return { accessToken, user, profile }

2. TOKEN STORAGE (Frontend):
   - localStorage.setItem('accessToken', token)
   - localStorage.setItem('user', JSON.stringify(user))

3. REQUEST AUTHENTICATION:
   - axios interceptor adds: Authorization: Bearer ${token}
   - Backend auth middleware extracts token
   - jwt.verify(token, JWT_SECRET)
   - req.user = { id: decoded.id, role: decoded.role }

4. SOCKET AUTHENTICATION:
   - Socket connects with: io(url, { auth: { token } })
   - Server middleware verifies JWT
   - User attached to socket.user
   - userSocketMap.set(userId, socketId)

5. TOKEN REFRESH:
   - Refresh token mechanism available
   - verifyRefreshToken() in jwtUtils
   - New access token issued

### 6.2 SERVICE DISCOVERY FLOW

1. SERVICE CATEGORIES:
   - GET /api/service-catalog
   - Returns Service categories with subServices

2. PROVIDER SEARCH:
   - GET /api/seeker/services or /api/service-catalog
   - Query params: category, city, lat, lng, radius

3. GEOSPATIAL QUERY:
   - MongoDB 2dsphere index on provider coordinates
   - $near or $geoWithin operators
   - Distance calculated in kilometers

4. RESULTS PROCESSING:
   - Sort by: rating, distance, price
   - Filter by: isVerified, availability
   - Paginate results

5. MAP DISPLAY:
   - Leaflet renders markers
   - Popup shows provider info
   - Click marker → provider detail

### 6.3 BOOKING LIFECYCLE FLOW

STEP 1: CREATE BOOKING
User Action:
  - Select provider → Choose service → Pick date/time → Confirm
Frontend:
  - POST /api/bookings with form data
Backend:
  - Validate provider, availability, schedule
  - Calculate pricing
  - Create Booking document (status: pending)
  - Create Notification for provider
  - socketManager.emitToUser(provider.userId, 'booking:new', data)
Frontend Socket:
  - Receive 'booking:new' event
  - Update notifications list
  - Show toast notification

STEP 2: PROVIDER RESPONSE
Provider Action:
  - View booking → Accept or Reject
Backend (Accept):
  - PATCH /api/bookings/:id/accept
  - Update status to 'accepted'
  - Create notification for seeker
  - Emit 'booking:accepted'
Backend (Reject):
  - PATCH /api/bookings/:id/reject
  - Update status to 'rejected'
  - Store cancellationReason
  - Emit 'booking:rejected'

STEP 3: CANCELLATION
User/Provider Action:
  - Cancel booking with optional reason
Backend:
  - PATCH /api/bookings/:id/cancel
  - Verify ownership (seeker/provider)
  - Update status to 'cancelled'
  - Notify other party
  - Emit 'booking:cancelled'

### 6.4 NOTIFICATION FLOW

CREATION:
- Triggered by bookingController
- new Notification({
    userId: recipient,
    bookingId: booking._id,
    title, message, category, type, actionUrl, metadata
  })
- notification.save()

REAL-TIME:
- socketManager.emitToUser(userId, eventType, {
    booking: {...},
    notification: {...}
  })

FRONTEND HANDLING:
- SocketContext subscribes to events
- handleNewNotification(notification, eventType):
  * notifications.unshift(notification)
  * unreadCount++
  * trigger callbacks
- UI updates badge count

READ STATUS:
- GET /api/notifications → fetch all
- PATCH /api/notifications/:id/read → mark single
- Socket emits 'notification:count' with new total

### 6.5 SOCKET COMMUNICATION FLOW

SERVER SIDE:
server.js:
  - Create HTTP server
  - Initialize Socket.IO with CORS
  - socketManager.setIO(io)

Authentication:
  - io.use(middleware) for JWT verification
  - Token from socket.handshake.auth.token
  - User object attached to socket

Connection:
  - io.on('connection', (socket) => {...})
  - socketManager.addUserSocket(user._id, socket.id)
  - Log connection info

Events Emitted:
  - booking:new → Provider receives new booking
  - booking:accepted → Seeker sees acceptance
  - booking:rejected → Seeker sees rejection
  - booking:cancelled → Either party notified
  - notification:new → General notifications
  - notification:count → Unread count updates

Disconnection:
  - socket.on('disconnect', (reason) => {...})
  - socketManager.removeUserSocket(socket.id)
  - Log disconnection

CLIENT SIDE:
SocketContext:
  - useEffect on isAuthenticated change
  - Connect with token in auth object
  - Setup event listeners
  - Cleanup on unmount

Event Handling:
  - Each event type has dedicated handler
  - Updates state (notifications, unreadCount)
  - Triggers UI updates via callbacks

## 7. SECURITY ANALYSIS

### 7.1 JWT HANDLING

Token Generation:
- jwt.sign(payload, secret, options)
- Payload: { id: user._id, role: user.role }
- Options: { expiresIn: '7d' }

Token Verification:
- Middleware extracts from Authorization header
- jwt.verify(token, process.env.JWT_SECRET)
- Decoded payload attached to req.user

Storage Security:
- Frontend: localStorage (vulnerable to XSS)
- Backend: select: false on password field

Token Refresh:
- Refresh token mechanism available
- Separate endpoint for token renewal
- Short-lived access tokens recommended

### 7.2 ROUTE PROTECTION

Authentication:
- All /api routes require valid JWT (except /api/health)
- auth() middleware on protected routes

Role Authorization:
- auth(['provider']) - Provider only
- auth(['seeker']) - Seeker only
- auth(['admin']) - Admin only

Frontend Routes:
- ProtectedRoutes component
- Checks isAuthenticated, role, verification status
- Redirects to /login, /unauthorized, or /verify

### 7.3 INPUT VALIDATION

Backend:
- Joi schemas in validation middleware
- express-validator for route-level validation
- Mongoose schema validation with custom messages
- Example: email regex, phone format, password minlength

Frontend:
- Form validation before submission
- Required field checks
- Format validation (email, phone)

### 7.4 ROLE AUTHORIZATION

User Roles:
- seeker: Can browse, book, review
- provider: Can manage services, accept/reject bookings
- admin: Full platform access

Authorization Checks:
- Booking ownership: seekerId/providerId match
- Profile access: userId reference
- Admin routes: auth(['admin']) middleware

### 7.5 DATA EXPOSURE RISKS

Password Storage:
- ✅ bcrypt hashed with salt
- ✅ select: false prevents accidental exposure

API Responses:
- ✅ User.toJSON removes password, __v
- ⚠️ Some endpoints may return sensitive data (review implementation)

Error Messages:
- ✅ Only in development mode
- ✅ Generic messages in production

Rate Limiting:
- ✅ 100 requests/15 minutes per IP
- ⚠️ Could be stricter for auth endpoints

CORS:
- ✅ Whitelist: frontend (5173), admin (5174)
- ⚠️ Consider environment-based configuration

Socket Security:
- ✅ JWT validated on handshake
- ⚠️ No room/namespace isolation visible
